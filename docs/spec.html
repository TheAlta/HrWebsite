«درباره من» یا «درباره ما»؟

اگر خودتان چهره اصلی برند هستید (که برای مشاور منابع انسانی معمولاً قوی‌ترین حالت است)، از «درباره من» استفاده کنید؛ اعتماد در خدمات مشاوره‌ای به شخص بسته است نه به شرکت. اگر قصد دارید تیم یا همکار اضافه کنید، ساختار را طوری بسازید که صفحه «درباره من» بعداً به «درباره ما» با بخش «تیم» قابل تبدیل باشد (موجودیت «عضو تیم» از اول در مدل داده وجود داشته باشد).

درخواست کاربر از CDN و Nginx به Django می‌رسد؛ کارهای کند (پیامک، ایمیل، ساخت PDF، یادآورها) به Celery سپرده می‌شوند تا صفحه منتظر نماند. همه خریدها از ماژول «سفارش و پرداخت» عبور می‌کنند.

اصول معماری

  • یک مسیر سفارش و پرداخت برای همه: رزرو، رویداد و فروشگاه فقط Order می‌سازند و به سیگنال order_paid گوش می‌دهند؛ ماژول پرداخت از جزئیات آن‌ها خبر ندارد.
  • وابستگی یک‌طرفه: اپ‌های دامنه (booking، events، shop) به orders وابسته‌اند، نه برعکس. notifications به هیچ اپ دامنه‌ای وابسته نیست.
  • لایه سرویس: منطق کسب‌وکار در services.py هر اپ، نه در view یا مدل؛ view فقط ورودی را اعتبارسنجی و سرویس را صدا می‌زند.
  • آداپتر برای سرویس‌های بیرونی: payments/gateways/ و notifications/providers/ با یک interface مشترک.
  • رندر سمت سرور + HTMX: صفحات برای سئو کامل از سرور می‌آیند؛ بخش‌های تعاملی (انتخاب زمان، سبد، اعمال کد تخفیف) با HTMX بدون رفرش به‌روز می‌شوند.
  • API آماده آینده: Django Ninja در /api/v1/ برای بخش‌های تعاملی؛ همان API بعداً برای اپ موبایل قابل استفاده است.
